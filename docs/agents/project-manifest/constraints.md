# Constraints & Conventions

## Code Style

- **Strict types:** Every PHP file declares `declare(strict_types=1)`.
- **PHP 8.4 baseline:** PHP 8 constructs are fully available — typed properties, union types, constructor promotion, `readonly`, named arguments, match expressions, enums, nullsafe operators. There is no PHP 7 compatibility requirement of any kind. All new code uses PHP 8 constructs; the `@var`-docblock property style in existing `src/` files is legacy, not a convention to copy. Existing code may be modernised opportunistically, in the same pass as any work that already touches it — no separate approval, plan, or cleanup task is required to bring a touched file up to PHP 8 standards. A wholesale sweep of untouched files remains out of scope for any given plan.
- **Namespace:** `Mistralys\ComposerSwitcher` for core classes, `Mistralys\ComposerSwitcher\Utils` for utility classes, `Mistralys\ComposerSwitcher\State` for the immutable value objects returned by the switcher's public methods (`SwitchOutcome`, `SwitchMessage`, `SwitchDescription`, `FileOperation`, `ConfigChange`, `ConfigChangeOrigin`, `ConfigChangeSet`).

## Error Handling

- All error codes use a `1821xx` numbering scheme — the exception class owns `182101`–`182116` (`182111`/`ERROR_INVALID_RECONCILE_DIRECTION` is retired, not reused; `182112`–`182116` are the entry-point edge's `ERROR_COMPOSER_COMMAND_FAILED`/`ERROR_COMPOSER_BINARY_NOT_FOUND`/`ERROR_SWITCH_BLOCKED`/`ERROR_CONFIRMATION_REQUIRED`/`ERROR_INPUTS_CHANGED`, thrown by `Utils\SwitchCommandRunner`/`Utils\ComposerProcess` — see [data-flows.md](data-flows.md)'s §7a), and the switcher class owns `182201`–`182229` (message codes; `182213`/`MESSAGE_DRY_RUN_ACTIVE` is reported by `previewSwitch()`/`switchTo($mode, true)`; `182214`/`MESSAGE_PROD_LOCK_MISSING` is emitted by `switch_planDevToProd()`, the DEV→PROD row of the v3 decision table's `switch_plan()` planner, when a DEV→PROD switch finds no `composer-prod.lock` snapshot backup to restore; `182217`–`182221` and `182225`–`182227` are the v3 decision table's own blocking/carry-back/cleanup/planning messages — see [switching-decision-table.md](switching-decision-table.md); `182222`–`182224`/`182228`–`182229` (`MESSAGE_COMPOSER_COMMAND`/`MESSAGE_COMPOSER_SKIPPED`/`MESSAGE_NESTED_RUN_SKIPPED`/`MESSAGE_CONFIRMATION_REQUIRED`/`MESSAGE_SWITCH_CANCELLED`) are the entry-point edge's own messages, written through `Utils\EventContext::writeMessage()` rather than accumulated on `ConfigSwitcher::getMessages()`). The retired v2 constants `182202`/`182207`/`182208` (`MESSAGE_CREATE_NEW_LOCK_FILE`/`MESSAGE_RUN_INSTALL_PROD`/`MESSAGE_RUN_INSTALL_DEV`) no longer exist — their only callers were the four `switch_case_*` methods the decision table replaced; the retired reconcile-family constants `182205`/`182206`/`182210`–`182212`/`182215`/`182216` (`MESSAGE_BACKED_UP_MAIN_TO_PROD`/`MESSAGE_RESTORED_PROD_TO_MAIN`/`MESSAGE_ALREADY_IN_SYNC`/`MESSAGE_RECONCILE_AMBIGUOUS`/`MESSAGE_DEV_MODE_NOT_RECONCILABLE`/`MESSAGE_INITIAL_NOT_RECONCILABLE`/`MESSAGE_PROD_CONFIG_MISSING`) no longer exist either — their only caller was the now-deleted `reconcile()`/`reconcileCore()` family.
- A missing lock file no longer aborts a switch: `switchTo()` (and its `switchToDevelopment()`/`switchToProduction()` wrappers) records `MESSAGE_NO_LOCK_FILE_FOUND`/`MESSAGE_PROD_LOCK_MISSING` as a warning and completes the config rewrite, status file, and flag file regardless. There is no remaining early-return path that leaves a switch half-done.
- `ComposerSwitcherException` also carries an optional, fluent `setContext(array $context): self` / `getContext(): array` / `getContextValue(string $key): mixed` payload for structured data beyond the free-form message. Every throw site in the library attaches context: `KEY_FILE_PATH`/`KEY_TARGET_PATH` for file-path-carrying failures (a copy's source under `KEY_FILE_PATH`, its destination under `KEY_TARGET_PATH`), `KEY_MODE` for `ERROR_INVALID_SWITCH_MODE`, `KEY_EXPECTED`/`KEY_ACTUAL` for the offending-value-plus-expected-set cases, `KEY_PACKAGE_NAME` where a local-repository entry is being processed, and `KEY_NATIVE_ERROR` for every real-mode `FileSystem` failure (`read()`/`write()`/`copy()`/`delete()`), holding the captured native PHP error message. A programmatic consumer never needs to parse the free-form message to recover this data.
- Errors are thrown as `ComposerSwitcherException` with an integer error code constant. No other exception types are used.
- `FileSystem`'s real-mode `read()`, `write()`, `copy()`, `delete()` and `modifiedTime()` never let a native PHP warning escape the facade: each routes its native call through a private `runNative()` helper that installs a temporary `set_error_handler()`, captures any warning as an `\ErrorException` (message/severity/file/line), and restores the previous handler (whatever it was, including none) via `restore_error_handler()` in `finally` — this is what keeps an I/O failure inside a Composer script surfacing only as the library's typed `ComposerSwitcherException`, never as the bare `\ErrorException` Composer's own `ErrorHandler::handle()` would throw for an unsuppressed warning. Every real-mode throw site chains that captured error as `getPrevious()` in addition to recording its message under `KEY_NATIVE_ERROR`.

## File-System Write Choke-Point

- Every mutating file operation performed by the library (`write()`, `copy()`, `delete()`) — and every read/existence/mtime check that must observe those writes consistently — passes through a single `Mistralys\ComposerSwitcher\Utils\FileSystem` facade. `ConfigSwitcher` constructs one `FileSystem` and propagates it to every `BaseFile` it owns (`$mainFile`, `$prodFile`, `$devFile`, `$statusFile`, every `FlagFile`) via `setFileSystem()` — never construct or call a mutating PHP filesystem function (`file_put_contents()`, `unlink()`, `copy()`) directly from `ConfigSwitcher` or a `BaseFile` subclass; go through the shared `FileSystem` instead. The sole exception is `ConfigSwitcher::installGitHooks()`, which calls `copy()`/`chmod()` directly against `.git/hooks/pre-commit` — a one-time, non-switching operation outside the dry-run-observable switch/preview code paths, so it is intentionally not routed through `FileSystem`.
- `FileSystem::setDryRun(true)` swaps `write()`/`copy()`/`delete()` to an in-memory overlay instead of touching disk, while `exists()`/`read()`/`modifiedTime()` consult that overlay first — this is what makes `ConfigSwitcher::previewSwitch()` run the exact same code path as a real switch with zero special-cased preview logic to drift out of sync.
- `FileSystem::getOperations()` is the source of truth for `SwitchOutcome::getOperations()`; `clearOperations()` is called at the start of every `switchTo()` call so each returned outcome only reflects that single call. Under the v3 decision table, `switch_planProdToProd()` (the PROD/INITIAL→PROD row) has no file effects beyond legacy cleanup/status/flags — `composer-prod.json`/`.lock` are not committed baselines to reconcile against, so a PROD→PROD switch has nothing further to copy.
- `BaseFile::tryCopyTo(BaseFile $target)` copies only when the source file exists — unlike checking the target's existence, it tolerates a missing *target* (the copy still runs to create it) and simply no-ops when the *source* is absent instead of throwing `ERROR_CANNOT_COPY_FILE`. `switch_planProdToDev()`'s snapshot-lock-file-backup call uses `tryCopyTo()` for exactly this reason: the main config's lock file is not guaranteed to exist when snapshotting it into `composer-prod.lock`.

## Production Snapshot Model (v3)

- `composer-prod.json`/`.lock` are now a **strictly transient** snapshot of a DEV session, not a committed, user-editable baseline: `switch_planProdToDev()` creates them from `composer.json`/`.lock` on a PROD/INITIAL→DEV switch, and `switch_planDevToProd()` deletes them once their content has been applied back onto the main files on a DEV→PROD switch. A PROD/INITIAL→PROD switch (`switch_planProdToProd()`) never touches them. `switch_cleanLegacyArtifacts()`, run at the start of every switch, deletes a committed-style `composer-prod.json`/`.lock` found while in PROD/INITIAL mode (recording `MESSAGE_LEGACY_FILES_FOUND`) — a v2-era artifact that has no reason to exist outside an active DEV session under v3.
- The status file records a `snapshotHash` (a hash of the snapshot config + lock content at the moment it was taken) and the `appliedRepositories` list. `switch_isSnapshotModified()` compares the snapshot's current content against that hash to detect tampering ahead of a DEV→DEV refresh or a DEV→PROD switch, blocking with `MESSAGE_SNAPSHOT_MODIFIED` (no file effects) rather than trusting an edited snapshot as the three-way revert's base/target. A missing stored hash (a legacy status file, or one written before `snapshotHash` existed) skips the tamper check entirely.
- DEV-time edits are carried back via `DevConfigTransformer::revert()`'s three-way diff (base = `apply($snapshot, $appliedRepos, $prodLock)`, current = the live DEV `composer.json`, target = `$snapshot`), not by restoring a saved file: a managed (local) package entry always takes the snapshot value (recording `MESSAGE_MANAGED_ENTRY_OVERRIDDEN` if the user edited it anyway), while every other key/package takes the current value, carrying a `composer require`/`remove`/config edit back into production (`MESSAGE_DEV_CHANGES_CARRIED_BACK` when the resulting `ConfigChangeSet`'s `prodConfig` section is non-empty). See [switching-decision-table.md](switching-decision-table.md) for the exact per-row effects.

## Entry-Point Edge (Confirmation & Execution)

- **Plan in the core, execute at the edge:** `ConfigSwitcher::switchTo()`/`previewSwitch()` never execute Composer or prompt the user — they only ever return a `SwitchOutcome` carrying at most one planned `Utils\State\ComposerCommand`. The only place in the library that executes Composer or prompts is `Utils\SwitchCommandRunner`, which every `composerSwitch*`/`composerSwitchPreview*` static entry point builds (via `ConfigSwitcher::buildRunner()`) and delegates to immediately. A library consumer who wants the same one-command behavior runs `getComposerCommand()` through `Utils\ComposerProcess` (or their own runner) themselves.
- **No write before confirmation:** `SwitchCommandRunner::runSwitch()` always previews and renders first; it only calls `switchTo()` for real (the only call that writes to disk) after the user has confirmed, or after confirming it wasn't required (`--yes`, or no `composer.json` change at all).
- **Non-interactive runs need `--yes`:** a non-interactive context without `--yes` prints the changes, then throws `ComposerSwitcherException::ERROR_CONFIRMATION_REQUIRED` rather than guessing - auto-proceeding would make confirmation meaningless for agents/CI.
- **The second-preview `hasSameEffectsAs()` check:** after confirmation, `runSwitch()` previews a second time and compares it against the first via `SwitchOutcome::hasSameEffectsAs()` before writing - a mismatch throws `ERROR_INPUTS_CHANGED` and writes nothing, closing the gap between what was shown and what gets applied without a second, hand-maintained diff implementation.
- **Entry-point control flow lives in `Utils\SwitchCommandRunner`; Composer event duck-typing lives only in `Utils\EventContext`.** `EventContext::fromEvent(?object $event)` is the sole `method_exists()` probing site for Composer's event/IO (`getArguments()`/`getIO()`/`isInteractive()`/`askConfirmation()`/`write()`); every other class (`SwitchCommandRunner`, `OutcomeRenderer`, `ConfigSwitcher`'s entry points) consumes the typed `EventContext` instead of the raw `?object $event`.
- **The nested-run guard:** `SwitchCommandRunner::runSwitch()` no-ops (writing `MESSAGE_NESTED_RUN_SKIPPED`, no preview, no file effects) when `COMPOSER_SWITCHER_NESTED` is set in the environment - i.e. this process was itself launched by `Utils\ComposerProcess::run()` (which always sets it in the child's environment). This is what keeps a consumer's leftover `post-update-cmd: @composer switch-update` hook safe: it no-ops inside a switcher-launched child process, and runs as an ordinary, idempotent refresh otherwise.
- **Flags are read from the Composer script arguments**, after Composer's own `--` separator (e.g. `composer switch-dev -- --yes`): `--yes` (skip confirmation), `--no-install` (print the planned command instead of running it), `--with-dependencies` (forwarded only to a partial `update <packages>` command, never a full `update` or `install`). `--no-interaction` is never read from the arguments - it is appended to the child command automatically whenever the parent `EventContext` is non-interactive.

## File Conventions

- **Status file path** is derived from the dev config path by replacing `.json` with `.status`.
- **Lock file path** is derived from any `ConfigFile` path by replacing `.json` with `.lock`.
- **Flag file path** is derived from the main file path by appending `.DEV` or `.PROD`.
- These path derivations use simple `str_replace()` — filenames must end in `.json`.
- Paths stored in the status file are canonicalized via `realpath()` (fallback to raw path when the file does not exist yet).

## Three-Path Convention

The `fromProjectRoot()` factory and all built-in Composer entry points assume the standard file layout:

- `<root>/composer.json` — mutable working copy, the only committed, hand-editable configuration
- `<root>/composer/composer-prod.json` — transient DEV-session snapshot (see "Production Snapshot Model (v3)" above); created and deleted automatically, never committed or hand-edited
- `<root>/composer/local-repositories.json` — local repository definitions

Projects that follow this convention can wire the built-in entry points directly in `composer.json` with zero PHP glue code.

## Configuration Format

- The dev config file must contain a `local-repositories` key with an array of objects, each having `package-name` (string) and `path` (string). An optional `version` (string) overrides the default `*` version constraint.
- Package names with underscores are also matched with hyphens when looking up existing repository entries (handles GitHub URL normalization).
- When a `local-repositories` package exists in `require-dev` (not `require`) in the PROD config, the DEV switch writes the version constraint to `require-dev` — it does not move the package to `require`.

## Testing

- Tests use **PHPUnit >=13.0** with classmap autoloading from `tests/TestClasses/`.
- Test suite directory: `tests/TestSuites/` (suffix `.php`).
- Each test copies the fixture from `tests/assets/test-project/` into an ephemeral directory under `tests/assets/work-projects/`. The directory is cleaned up on tearDown unless `setKeepWorkFiles()` is called or the test failed.
- The `work-projects/` directory contains only transient test data and should not be committed.
- `tests/bootstrap.php` (wired via `phpunit.xml`'s `bootstrap` attribute) calls `WorkCopy::purgeStale()` against `tests/assets/work-projects` once per PHPUnit process, so abandoned work copies from failed/kept-alive runs (e.g. via `setKeepWorkFiles()`) get swept up on the next run regardless of entry point (`composer test`, `test-file`, `test-filter`, or a direct/IDE invocation) — entries younger than `WorkCopy::STALE_AFTER_SECONDS` (86400s / 24h) are left untouched so concurrent Tier 1/Tier 2 sessions don't purge each other's in-flight work copies.
- `ComposerSwitcherTestCase::tearDown()` determines pass/fail via `$this->status()->isFailure() || $this->status()->isError()`, the PHPUnit 10+ replacement for the removed `hasFailed()` method. The `composer.json` floor of `>=13.0` now matches what this call site requires.
- `phpunit.xml` uses the current PHPUnit 13 attribute set (XSD reference, `cacheDirectory=".phpunit.cache"`) and runs with zero configuration-schema deprecations. It also sets `failOnWarning="true"` and `failOnNotice="true"`, so a run reporting any warning or notice fails outright instead of printing "OK, but there were issues!" — a source-level fix is required, never suppression in the test.
- The dev toolchain (PHPUnit 13) needs PHP `>=8.4.1` to install (`vendor/phpunit/phpunit/composer.json`); the runtime `php` constraint stays `>=8.4` so consumers are unaffected — only a PHP 8.4.0 development environment loses the ability to install the dev toolchain.

### Test Conventions

- Every external process spawned by a test goes through a runner (`ComposerRunner`, `GitRunner`) using Symfony `Process`'s array-argument form — never a shell string, `exec()`, or `shell_exec()`.
- Any test that spawns `git` or Composer belongs in Tier 2 (`tests/IntegrationSuites/`), even if it can run offline.
- Fail-fast Composer calls use `IntegrationTestCase::runComposerChecked()`.
- Placeholder-substituted fixtures are verified by asserting the literal placeholder value, not by asserting the absence of a leak pattern.
- Mtime ordering between files is forced with `touch()`, never `sleep()`.
- Tests never mutate the shared clone cache (`tests/assets/local-clones/`) directly — inject a throwaway cache directory (e.g. via `WorkCopy::allocate()`) instead.
- Adding a new class under `tests/TestClasses/` requires running `composer dump-autoload` (classmap autoloading).
- `FixtureFileSystem::pathExists()` is the harness's single dangling-symlink-aware path-existence predicate (`is_dir || is_file || is_link`) — shared by `FixtureFileSystem::copyDirectory()` and `WorkCopy`. Any new harness code that needs to check whether a path exists (including a possibly-dangling symlink) should call this rather than a bare `file_exists()`, which returns `false` for a dangling symlink and would misreport it as absent.
- New Tier 1 coverage added alongside the value-object/`FileSystem`/structured-message rework: `TestMessages.php` (message-code typing and legacy text parity), `TestExceptionContext.php` (`ComposerSwitcherException` context payload), `TestDescribe.php` (`describe()`/`SwitchDescription`), `TestDryRun.php` (`previewSwitch()`/dry-run parity, including a static `src/` filesystem choke-point guard scan), `TestFixtureFileSystem.php`, and `TestBootstrap.php`. See [file-tree.md](file-tree.md) for the full per-file description of every suite.

### Test Tiers

- **Tier 1** (`tests/TestSuites/`, run via `composer test`): fast, hermetic tests with no network access or external binaries required. Extend `ComposerSwitcherTestCase` directly and copy the `test-project` fixture.
- **Tier 2** (`tests/IntegrationSuites/`, run via `composer test-integration`): real-world validation against an actual `git` clone and the real `composer` binary. Extend `IntegrationTestCase` (itself a subclass of `ComposerSwitcherTestCase`), which copies the `integration-project` fixture instead of `test-project`.
  - `IntegrationTestCase::setUp()` resolves a cached local package clone via `LocalPackageClone` and calls `markTestSkipped()` (not a failure) with a cause-naming message when git, the network, or the Composer binary is unavailable — Tier 2 suites are expected to skip gracefully in constrained environments (e.g. CI sandboxes without network egress). The invalid-directory skip message additionally names the offending cache directory path and tells the reader to delete it to re-clone.
  - `LocalPackageClone` acquires its cache atomically: `git clone` always lands in a uniquely-named `.partial-*` sibling first and is only `rename()`d onto the cache path once its `composer.json` is verified present, so `REASON_INVALID_DIRECTORY` can only mean a directory that is invalid for some other reason (e.g. hand-edited), never an interrupted clone. Stale `.partial-*` siblings older than `PARTIAL_STALE_AFTER_SECONDS` (600s) are purged on every `ensureAvailable()` call. Both the cache directory and repository URL are constructor-injectable, which is what lets `tests/TestSuites/TestLocalPackageClone.php` (Tier 1) exercise every code path via a throwaway `WorkCopy::allocate()` directory without ever touching the real, shared cache that Tier 2 suites reuse across concurrent sessions.
  - The `integration-project` fixture ships two unresolved placeholders — `__LOCAL_CLONE_PATH__` (in `composer/local-repositories.json`) and `__LIBRARY_SRC_PATH__` (in `composer.json`) — which `setUp()` substitutes in the ephemeral work copy only; the committed fixture files are never modified. There is no committed `composer/composer-prod.json` fixture to substitute under the v3 transient-snapshot model (see "Production Snapshot Model (v3)" above) — that file only ever exists as a runtime-created snapshot during an active DEV session.
  - `IntegrationTestCase` exposes `bootstrapProd()` (runs `composer update` once to produce a real `composer.lock` and `vendor/` tree), `runComposer(string ...$arguments): ProcessResult` (delegates to a `ComposerRunner` bound to the work copy), `runSwitch(string $script, string ...$scriptArgs)` (runs a `composer switch-*` script via the unchecked `runComposer()`, appending `-- --yes` plus the given arguments, so every Tier 2 switch call goes through the new v3 confirmation requirement without a hand-rolled argument list), and `setLocalRepositoryVersionOverride(?string $version)` (adds/removes the optional `version` key in the work copy's `local-repositories.json`).
  - `IntegrationTestCase` also owns the shared Tier 2 helper set, hoisted out of the individual suites to remove duplication: `runComposerChecked(string ...$arguments): ProcessResult` (fails the test with the command, exit code, and both output streams on a non-zero exit); `switchToDev(): void` (`bootstrapProd()` then a checked `switch-dev`); `updateDependencies(): void` (a checked `composer update`); `readFile(string $path): string`; `decodeJsonFile(string $path): array` (reads and JSON-decodes, failing the test if the result isn't an array); and `writeJsonFile(string $path, array $data): void` (pretty-printed, unescaped slashes, trailing newline). Every consuming suite under `tests/IntegrationSuites/` must call these inherited methods rather than defining a private equivalent — `bootstrapProd()` itself is implemented in terms of `runComposerChecked('update')`.
  - `ComposerRunner` shells out to the real `composer` binary against a given work copy and returns a `ProcessResult` (exit code, stdout, stderr); it reuses the ambient `COMPOSER_HOME` for cache/auth so runs stay fast, while the test project's own `vendor/` lives inside the ephemeral work directory and is discarded on teardown.
  - `GitRunner` is the single choke-point for every `git` invocation in the harness: it constructs `Symfony\Component\Process\Process` exclusively via the array-argument form (no shell string interpolation), always resolves the `git` binary through PATH (never a user/environment-controllable override), and returns the same `ProcessResult` shape as `ComposerRunner`. `isAvailable()` runs `git --version` and catches `Throwable` rather than letting a missing binary propagate as an uncaught exception.
- Test command reference: `composer test` (Tier 1 only), `composer test-integration` (Tier 2 only), `composer test-file -- <path>`, `composer test-suite -- <name>`, `composer test-filter -- <pattern>`, `composer test-group -- <group>`.

## Bundled Resources

- Non-PHP assets (e.g. shell scripts) live under `resources/` in the library root and are shipped with the Composer package.
- `resources/git-hooks/pre-commit` is the canonical shared pre-commit hook. Consumer projects install it via `ConfigSwitcher::installGitHooks()`. Guard 2 (the local path-repository block) scopes its check to the staged `composer.json`'s `repositories` key via a fail-safe `php -r` JSON parse (list or keyed-object form, non-array entries skipped), using three dedicated exit codes outside `0`, `1`, `2`, `127` and `255`; only a confident "none found" result passes directly, and every other outcome — a path repository found, undecodable JSON, a missing `php` binary, or a crashing one — falls back to the original file-wide grep, which never fails open.

## Workflow Rules

- **In PROD mode, `composer.json` is the source of truth** — edit it directly. `composer-prod.json`/`.lock` are a strictly transient DEV-session snapshot under the v3 model (see "Production Snapshot Model (v3)" above) and must never be edited by hand; any edit to them is silently discarded the moment `switch_planDevToProd()` consumes and deletes them. In DEV mode, edits to `composer.json` (including `composer require`/`remove`) are kept and carried back into production on the next `switch-prod` (`DevConfigTransformer::revert()` — check `composer switch-describe`'s `pendingProdChanges` for what would be carried back).
- Console output is **off by default** (`ConsoleWriter` starts disabled). Call `setWriteToConsole(true)` to enable verbose logging.
- Flag files are **on by default**. Call `setFlagFileEnabled(false)` to disable.
