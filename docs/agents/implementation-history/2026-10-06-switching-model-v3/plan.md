## Summary

This plan reshapes the switching model so that it can't lose data, can't drift, and finishes in one
command. Six rules replace the current model:

1. **`composer.json` is the single source of truth for production.** `composer-prod.json`/`.lock`
   stop being committed duplicates. They become a transient snapshot that `switch-dev` takes and
   `switch-prod` consumes and deletes. PROD mode then has nothing to drift against, so
   `reconcile()`, `verify()` and their states are removed.
2. **Edits made in DEV are kept.** Leaving DEV performs a three-way revert of the DEV transform:
   changes the user made, including `composer require` and `remove`, are carried back into the
   production config instead of being overwritten.
3. **DEV is PROD plus the switched packages.** The DEV lock starts from the PROD lock, and only the
   local packages are updated (`composer update <local packages>`). Everything else stays at
   production versions. No DEV lock is ever restored, so a stale DEV lock cannot exist.
4. **No version pin to maintain.** Each local package is aliased to the version production has
   locked, which satisfies every constraint production already satisfies. The optional `version`
   override stays for edge cases.
5. **One command.** `switch-dev`, `switch-prod` and `switch-update` run the required Composer step
   themselves (`install`, a partial `update`, or `update --lock`), chosen from the lock's
   `content-hash` and the installed state. `--no-install` opts out.
6. **Nothing changes without being shown and confirmed.**
   - Before any switch writes to `composer.json`, it prints every change to the config,
     entry by entry. Version and constraint changes are marked, and so are DEV edits that are
     about to become permanent in the production config. It also prints the Composer command it
     will run.
   - It then asks for confirmation.
   - Non-interactive runs (agents, CI) must pass `--yes` to apply when `composer.json` would
     change. Without it, the changes are printed and the switch exits non-zero with nothing
     written. A switch that leaves `composer.json` unchanged (e.g. PROD→PROD `install`) needs no
     `--yes`.
   - A leftover `post-update-cmd: @composer switch-update` hook stays harmless: it is skipped
     inside switcher-launched Composer runs, and after a user-run `composer update`/`require` it is
     a refresh that leaves `composer.json` unchanged, so it neither prompts nor needs `--yes`.

`describe()` reports config mode, lock status, installed state, and the DEV changes pending
carry-back. This is a breaking release: v3.0.0.

## Approach / Architecture

### File model (v3)

| File | Committed | Exists | Role |
|---|---|---|---|
| `composer.json` / `composer.lock` | Yes | Always | PROD truth in PROD mode. The DEV working copy in DEV mode. |
| `composer/composer-prod.json` / `.lock` | **No** (gitignored) | DEV mode only | Snapshot of PROD taken by `switch-dev`, consumed and deleted by `switch-prod` |
| `composer/local-repositories.json` | No | Optional | Local list: `package-name`, `path`, optional `version` override |
| `composer/local-repositories.status` | No | After the first switch | Mode, date, paths, **snapshot hash**, **applied repositories** |
| `composer.json.DEV` / `.PROD` | No | Per mode | Flags (unchanged) |
| `composer/local-repositories.lock` | — | **Retired** | Deleted on sight as a legacy file |

### New and reshaped components

1. **`Utils\ComposerContentHash` (new):** `fromConfigData(array): string`, an exact mirror of
   `Locker::getContentHash()` (carried over from the superseded plan).
2. **`State\LockStatus` (new enum):** `Missing | Fresh | Stale | Unknown`, plus `requiresUpdate()`.
3. **`Utils\LockFile` (extended):**
   - `getContentHash(): ?string`;
   - `getLockStatus(): LockStatus`, checked against its own config;
   - `getLockedVersion(string $package): ?string`, which reads `packages` and `packages-dev`.
   - All three never throw and never cache.
4. **`State\LocalRepository` (new value object):**
   - holds `packageName`, `path` and `?versionOverride`;
   - static `parseList(array $data, string $filePath): LocalRepository[]` is the single validator,
     replacing the two duplicated parsers. It throws the existing `ERROR_INVALID_JSON_STRUCTURE`
     with context.
   - `describe()` keeps its lenient behaviour without a second validator. A lenient sibling
     `parseListLenient(array $data, string $filePath): array{LocalRepository[], string[]}` runs the
     same per-entry check as `parseList()`. It skips a malformed entry with the existing warning
     text "Skipped a malformed entry in the dev configuration [local-repositories] list." and
     returns the remaining entries, and it returns the existing "does not contain a valid
     [local-repositories] list." warning for a missing or non-list key. A wrapping `catch` would
     not be enough, because it would drop the whole list where today only the bad entry is
     skipped.
   - `toArray()` / `fromArray()` are used for the status file.
5. **`Utils\DevConfigTransformer` (new):** extracted from `switch_adjustConfigForDev()`.
   - `apply(array $prodConfig, LocalRepository[] $repos, LockFile $prodLock): DevTransformResult`.
     For each local package:
     - The alias version is `versionOverride ?? $prodLock->getLockedVersion($name)`.
     - The root constraint is kept from prod when the package is root-required and an alias exists.
     - Otherwise the constraint is `*`, added to `require`, or to `require-dev` when it lives there.
     - The path repository is `{type: path, url, options: {symlink: true, versions: {…}}}`, with the
       underscore/hyphen alias, and with `versions` omitted when no version can be derived.
     - The existing URL-match replace/prune/append logic is unchanged.
     - The returned result carries the config and the `MESSAGE_VERSION_DERIVED` facts, per package
       and per source.
   - `revert(array $devConfig, array $snapshotConfig, LocalRepository[] $appliedRepos, LockFile $prodLock): RevertResult`
     is a **three-way revert** with base `apply(snapshot)`, current `devConfig` and target
     `snapshot`:
     - A top-level key where `current == base` takes the `snapshot` value.
     - A key the transform never touches (`base == snapshot`) takes the `current` value, which is a
       user edit carried back.
     - For `require` / `require-dev`, entries are merged per package:
       - managed (local) packages always take the snapshot value, or are dropped when the snapshot
         has none; a managed entry the user edited is recorded as overridden;
       - every other package takes the current value, so additions, removals and constraint
         changes are carried back.
     - For `repositories`, the result is the snapshot list, plus current entries absent from base,
       minus base entries the user removed (excluding managed path entries).
     - The result carries `effectiveConfig` and the overridden managed entries. What changed in
       production is not a separate value here: it is the `prodConfig` section of the
       `ConfigChangeSet`, diffed from snapshot → `effectiveConfig` (item 14).
     - Invariant: `revert(apply(P), P, repos) == P` for every P.
6. **Production change view (no separate type):** `ConfigChangeSet` (item 14) exposes
   `getProdChangedKeys(): string[]` (top-level keys that differ from the snapshot) and
   `getProdChangedPackages(): string[]` (root package names added, removed or re-constrained in
   `require`/`require-dev`), both derived from its `prodConfig` section. The planner, the
   confirmation output and `describe()` read the same object, so they can never disagree about
   what changed. (An earlier draft had a separate `State\ProdChanges` value object duplicating
   this section; it is folded in.)
7. **`State\InstalledState` (new enum) + `Utils\InstalledPackages` (new reader):**
   - `InstalledPackages` reads `<vendor-dir>/composer/installed.json` through `FileSystem`. The
     vendor dir comes from `config.vendor-dir`, defaulting to `vendor`.
   - It exposes `exists()` and `isInstalledFromPath(string $name): ?bool`.
   - `InstalledState` is `Matches | Pending | Unknown`. In DEV, it is `Matches` when every local
     package is path-installed. In PROD, it is `Matches` when none is.
8. **`State\ComposerCommand` (new value object):** an argument list without the binary (e.g.
   `['update', 'vendor/a', '--with', 'vendor/b:2.0.0']`), a `reason` text, `toArray()` and
   `toShellString()`.
9. **`Utils\ComposerProcess` (new, runtime):**
   - `run(ComposerCommand $command, string $workingDir): int` executes `[PHP_BINARY, COMPOSER_BINARY, …args]`.
     When `COMPOSER_BINARY` is unset, it falls back to a `composer` executable found on `PATH`.
     Otherwise it throws `ERROR_COMPOSER_BINARY_NOT_FOUND`.
   - It uses `proc_open` with the array form and inherited STDIN/STDOUT/STDERR. The environment is
     `getenv()` plus `COMPOSER_SWITCHER_NESTED=1`.
   - Native warnings are captured through a scoped error handler, as in `FileSystem`.
   - The binary path can be injected through the constructor for tests.
10. **`ConfigSwitcher` (reshaped):**
    - `switchTo()` keeps its signature and dry-run semantics. It now plans exactly one optional
      `ComposerCommand` per outcome, from a single post-dispatch planner, using the final state.
    - It **never executes** Composer. Execution happens only at the entry-point edge, so the API,
      previews and Tier 1 stay pure.
    - Blocked switches return an outcome with `isBlocked() === true`, a blocker message, and no file
      effects.
    - The reconciliation family and `verify()` are removed.
11. **`SwitchOutcome` (extended):**
    - getters `getComposerCommand(): ?ComposerCommand`, `isBlocked(): bool` and
      `getConfigChanges(): ConfigChangeSet`;
    - `requiresConfirmation(): bool`, which is true when the `composerJson` section is non-empty;
    - `hasSameEffectsAs(SwitchOutcome $other): bool`, which compares `isBlocked()`,
      `getConfigChanges()->toArray()`, `getComposerCommand()?->toArray()` and the file operations
      (type, source, target). Messages are not compared. This is the "shown equals applied" check
      used by the runner (item 15);
    - `toArray()` keys `composerCommand`, `blocked` and `configChanges`.
12. **`SwitchDescription` (reshaped):**
    - `verification` is replaced by `lockStatus: LockStatus`, `installedState: InstalledState` and
      `pendingProdChanges: ?ConfigChangeSet` (DEV only; only the `prodConfig` section is filled);
    - `localRepositories` entries gain `derivedVersion: ?string`;
    - legacy-file warnings are added.
13. **`StatusFile` (extended):** `snapshotHash` (md5 of snapshot config plus lock contents) and
    `appliedRepositories`. Legacy status files without them are tolerated: snapshot checks are
    skipped and the current list is used, both with a warning.
14. **`Utils\ConfigDiff` (new) + `State\ConfigChange` / `State\ConfigChangeSet` (new value
    objects) + `State\ConfigChangeOrigin` (new enum):**
    - `ConfigDiff::between(array $before, array $after, callable $classifier): ConfigChange[]` is a
      structural diff:
      - associative arrays recurse to leaf paths, e.g. `require › vendor/pkg`;
      - lists (`repositories`) are compared item by item by value, as added or removed items;
      - each change has a kind: `Added`, `Removed` or `Changed`.
    - `ConfigChange` holds `path` (segments), `before`, `after`, `kind` and `origin`, plus
      `isVersionChange()`. That is true for paths under `require`/`require-dev` or
      `repositories[…].options.versions`.
    - `ConfigChangeOrigin` is `LocalSwitch` (an entry the switcher manages), `CarriedBack` (a DEV
      edit becoming permanent in PROD) or `Discarded` (a DEV edit to a managed entry being reset).
      The classifier comes from `DevConfigTransformer`, which knows the managed entries and,
      through `RevertResult`, the overridden ones (`Discarded`).
    - The differ runs over the actual before/after arrays that are written, rather than having the
      transformer log its own operations. The shown set is therefore derived from the real output
      of every path, including the DEV→DEV refresh, where `revert` and `apply` compose.
    - `ConfigChangeSet` has two sections:
      - `composerJson`: `composer.json` before → after, present in every switch that writes the
        file;
      - `prodConfig`: snapshot → effective production config, DEV→PROD (and `describe()` in DEV),
        which shows the permanent changes.
      - It also provides `isEmpty()`, `hasPermanentChanges()`, `toArray()`, and the production
        change view `getProdChangedKeys()` / `getProdChangedPackages()` (item 6).
    - The planner fills the set during `switchTo()`, so a dry run (`previewSwitch()`) yields
      exactly the set a real switch would apply.
15. **`Utils\SwitchCommandRunner` (new, entry-point controller):**
    - Constructed with an `EventContext` (item 17), a `ConfigSwitcher`, a `ComposerProcess` and an
      `OutcomeRenderer`; all four are injectable, so Tier 1 tests target one class with no static
      state.
    - `runSwitch(string $mode): void` holds the whole confirmation sequence below, the nested-run
      guard, the `--yes` / `--no-install` / `--with-dependencies` parsing, `--no-interaction`
      forwarding, command execution and the exit-code / exception mapping.
    - `runUpdate(): void` does the same for `switch-update`, and `runPreview(string $mode): void`
      renders a preview and never executes.
    - **Shown equals applied:** the runner calls `previewSwitch()` once before the prompt and once
      after it. When `$second->hasSameEffectsAs($first)` is false (including a switch that has
      become blocked), it throws `ERROR_INPUTS_CHANGED` and writes nothing. This checks the
      invariant itself (the applied outcome equals the confirmed one), so it covers every input the
      planner reads, now and later, without a hand-maintained file list. Lock-content edits are
      covered too: they change the lock status (and therefore the command), or trip the snapshot
      hash (blocked).
16. **`Utils\OutcomeRenderer` (new):**
    - moves `printPreview()`/`formatOperation()` out of `ConfigSwitcher`;
    - renders change sets as a grouped list (marking version changes as `[version]`, carried-back
      entries as `[permanent]` and discarded entries as `[discarded]`), the planned command, and
      the file operations;
    - writes through `EventContext::write()`;
    - is used by `SwitchCommandRunner` (switch and preview) and by `composerSwitchDescribe()`
      (pending carry-back).
17. **`Utils\EventContext` (new adapter):**
    - `EventContext::fromEvent(?object $event): self` is the **only** place that duck-types
      Composer's event: it probes `getArguments()`, `getIO()`, and on the IO `isInteractive()`,
      `askConfirmation()` and `write()` with `method_exists`, once.
    - Typed API: `getArguments(): string[]`, `hasFlag(string $flag): bool`, `isInteractive(): bool`,
      `confirm(string $question, bool $default): bool` and `write(string $line): void`.
    - Fallbacks: no event → no arguments and non-interactive; no IO → `write()` echoes with
      `PHP_EOL`, as `printPreview()` does today; `confirm()` on a non-interactive context returns
      `false` (the runner never calls it there).
    - The class is not final, so the Tier 1 double `ScriptedEventContext` can extend it with
      queued answers.

### Confirmation (transparency)

`SwitchCommandRunner::runSwitch()` follows the same sequence every time:

1. `previewSwitch($mode)` (the first preview). When the outcome is blocked, render it and stop
   (`ERROR_SWITCH_BLOCKED`).
2. Render the change set and the planned command. This happens always, with or without `--yes`.
3. When `requiresConfirmation()` is false (no `composer.json` change, e.g. PROD→PROD `install`),
   skip to step 5.
4. Confirm:
   - `--yes` was given: confirmed.
   - Interactive context (`EventContext::isInteractive()`): ask
     `confirm("Apply these changes and run `composer …`?", $default)`.
     `$default` is `false` when the set has permanent or discarded changes, and `true` otherwise.
   - Non-interactive without `--yes`: emit `MESSAGE_CONFIRMATION_REQUIRED`, throw
     `ERROR_CONFIRMATION_REQUIRED`, and write nothing.
   - Declined: emit `MESSAGE_SWITCH_CANCELLED`, write nothing, exit 0.
5. Preview again. When the second outcome does not `hasSameEffectsAs()` the first, throw
   `ERROR_INPUTS_CHANGED` and write nothing.
6. Run the real `switchTo($mode)`, then execute its command (unless `--no-install`).

`switchTo()` itself never prompts. API callers inspect `getConfigChanges()` and decide. With
`--no-install`, steps 1–5 still apply; only the command execution is skipped. When step 3 skips the
prompt, step 5 still runs; it is a pure dry run and costs one extra in-memory switch.

### Switching decision rules (one planner, final state)

Every switch first cleans legacy files. It deletes `composer/local-repositories.lock`; when in
PROD/INITIAL with a committed-style `composer-prod.json` present, it overwrites it on `switch-dev`
or deletes it on `switch-prod`. Both emit `MESSAGE_LEGACY_FILES_FOUND`.

| From → To | Preconditions (blockers) | File effects | Planned Composer command |
|---|---|---|---|
| PROD/INITIAL → DEV | Main lock `Stale` blocks with `MESSAGE_PROD_LOCK_OUTDATED`. The PROD state is inconsistent before the switch starts, so the user must first run `composer update` (or `update --lock`) in PROD. | Snapshot the main config and lock into `composer-prod.*`, store `snapshotHash` and `appliedRepositories`, write `apply(snapshot)` into `composer.json`. `composer.lock` stays the PROD lock. | `update <all local package names>` (plus `--with-dependencies` when that flag is passed). When the main lock is `Missing`: full `update`, with `MESSAGE_NO_LOCK_FILE_FOUND`. |
| DEV → DEV (refresh, `switch-dev` or `switch-update`) | Snapshot modified (hash mismatch) blocks with `MESSAGE_SNAPSHOT_MODIFIED`. | `effective = revert(current, snapshot, appliedRepos)`, then write `apply(effective, currentRepos)` only when it differs from `current` (an empty `composerJson` section means no write, so the file's bytes are untouched). Any planned command adds `MESSAGE_COMPOSER_COMMAND` with text like
"Running `composer update vendor/a`: <reason>".

### Entry-point edge (static methods)

- **Signature and delegation:** every `composerSwitch*` takes `?object $event = null` and is a
  one-liner that builds `EventContext::fromEvent($event)` and a `SwitchCommandRunner` for
  `getcwd()`, then delegates (`runSwitch()`, `runUpdate()` or `runPreview()`). The statics hold no
  control flow, so the sequence is not added to the 1472-line orchestrator.
- **Arguments:** read from `EventContext::getArguments()` (the duck-typing lives only in
  `EventContext`, with no Composer type dependency). Supported: `--yes`, `--no-install` and
  `--with-dependencies`. The full sequence is in "Confirmation (transparency)" above.
- **Nested runs:** when `getenv('COMPOSER_SWITCHER_NESTED')` is set, `switch-dev`/`-prod`/`-update`
  emit `MESSAGE_NESTED_RUN_SKIPPED` and return. This makes a leftover `post-update-cmd` hook
  harmless and prevents recursion.
- **Hook on a user-run update:** when the user runs `composer update`, `require` or `remove`
  themselves with the `post-update-cmd: @composer switch-update` hook still wired,
  `COMPOSER_SWITCHER_NESTED` is unset and the guard does not apply. This is intended:
  `switch-update` runs as an ordinary refresh (DEV→DEV) or the PROD→PROD row, and no special-case
  code path is added. The outcome is safe by construction:
  - In DEV with an unchanged local list, the refresh computes `apply(revert(current))`, which equals
    `current`, because the user's edit is a non-managed entry that `revert` carries and `apply`
    leaves alone. The `composerJson` section is empty, so the refresh skips the write and Composer's
    bytes stay as written. `requiresConfirmation()` is false: no prompt,
    no `--yes` needed, even non-interactively. Composer has just installed the path packages, so
    the installed state is `Matches` and no command is planned.
  - In PROD, Composer's own update leaves the installed state `Matches`, so nothing is planned.
  - Only when `local-repositories.json` was edited since the last switch does the refresh have a
    delta. It then behaves as any `switch-update` does: interactive runs show the changes and ask;
    non-interactive runs print them and fail with `ERROR_CONFIRMATION_REQUIRED`, naming `--yes`.
    The user's own update has already completed, and the switcher writes nothing.
  - The docs still recommend removing the hook (Human Actions #2).
- **Blocked outcomes:** messages are printed, then `ComposerSwitcherException`
  (`ERROR_SWITCH_BLOCKED`) is thrown, so the script exits non-zero and agents see the failure.
- **Planned command:** with `--no-install`, `MESSAGE_COMPOSER_SKIPPED` is printed ("Run
  `composer …` to finish"). Otherwise `ComposerProcess::run()` executes it. A non-zero exit throws
  `ERROR_COMPOSER_COMMAND_FAILED` (context: command, exit code), and the message names the
  remediation, e.g. `composer switch-dev -- --with-dependencies` when a partial update fails.
- **Previews:** `switch-preview-dev`/`-prod` print "Would run: composer …" and never execute.
- **Removed entry points:** `composerSwitchReconcile` and `composerVerifyConfig`.
- **`composerSwitchDescribe`:** prints mode, lock status, installed state, pending carry-back
  (rendered as a change set by `OutcomeRenderer`), and local repositories with derived versions.

## Rationale

- **A single source of truth removes a whole class of states.** Every reconcile state ("ambiguous",
  "missing prod", mtime direction) exists only because two editable copies were committed. Making
  the copy a transient snapshot removes those states instead of handling them. About 300 lines of
  `src/` and the `TestReconcile` suite go away.
- **The three-way revert is what makes DEV edits safe.** The switcher knows exactly which entries it
  manages, so anything else that differs is by definition a user edit. A simple rule ("managed keys
  revert, others carry") handles `composer require`, `remove`, script and autoload edits, and added
  repositories. The round-trip invariant `revert(apply(P)) == P` makes the transform testable as a
  property.
- **Seeding DEV from the PROD lock gives fidelity and removes staleness by construction.** A partial
  update of only the local packages keeps every other version at production's. The restored-old-DEV-
  lock path is deleted, not patched.
- **Deriving the alias from the PROD lock answers the user's request.** The locked version is, by
  definition, a version satisfying every constraint production resolved, so aliasing the symlinked
  package to it keeps all root and transitive constraints satisfied. The `version` key becomes an
  optional override for packages production does not lock, such as a brand-new dependency.
- **Plan in the core, execute at the edge.** `switchTo()` stays pure: deterministic, dry-runnable,
  Tier 1-testable. Only the static entry points spawn Composer. API consumers get the same
  `ComposerCommand` and can run it with `ComposerProcess` or their own runner.
- **Blocking on a stale PROD lock** is preferable to a hidden full update of production
  dependencies. It happens only when the committed state is already inconsistent.
- **`update --lock` for relevant non-package edits** (e.g. `extra`, `minimum-stability`) refreshes
  the hash without moving versions. That is the same fidelity principle applied to PROD.
- **Confirmation lives at the edge and reuses the preview.**
  - `previewSwitch()` is already guaranteed to run the exact code path of the real switch, so the
    change set shown to the user is the change set applied. There is no second diff
    implementation that could drift.
  - Keeping prompts out of `switchTo()` keeps the core pure and the API unchanged; API callers get
    the same `ConfigChangeSet` to show however they like.
- **Two diff sections, because "what changes in `composer.json`" and "what changes in production"
  are different questions.**
  - On `switch-prod`, the composer.json diff is mostly the DEV transform being undone, which is
    routine.
  - The permanent production changes (carried-back DEV edits) are the part that needs a deliberate
    decision, so they get their own section. Their prompt defaults to "no".
- **Non-interactive runs need `--yes`, not an implicit "yes".** An agent or CI job has no one to
  confirm. Requiring an explicit flag keeps the switch a single command (`composer switch-dev -- --yes`)
  while making approval visible in the command itself. The changes are still printed in the output
  for the log. Running ahead silently would defeat the transparency goal.
- **The second preview** closes the gap between showing and applying. A user may edit files in
  their IDE while the prompt is open. Comparing the two outcomes checks the property AC-24 states
  (the applied set equals the confirmed one) instead of hashing a list of input files that every
  future planner input would have to be added to. Edits that do not alter the outcome (whitespace
  in `local-repositories.json`, say) no longer abort the switch.
- **The entry-point sequence gets its own class for the same reason rendering does.** Prompting,
  re-previewing, process execution and failure mapping are more new control flow than the
  rendering that is already being extracted from the orchestrator. `SwitchCommandRunner` gives
  three entry points one place to change, and gives the Tier 1 edge tests one injectable target.
- **Duck-typing is confined to one adapter.** The zero-dependency rule forces probing Composer's
  event by method name. `EventContext` does it once, and everything downstream takes a typed
  object, so PHPStan sees real signatures and one test double replaces two.
- **Every new abstraction has a current consumer:**

  | Abstraction | Consumers |
  |---|---|
  | `DevConfigTransformer` | All four switch paths and `describe()` |
  | `InstalledState` | The planner and `describe()` |
  | `ComposerCommand` | The planner, previews, entry points and the API |
  | `ComposerProcess` | `SwitchCommandRunner` |
  | `LocalRepository` | The transformer, the status file and `describe()` |
  | `ComposerContentHash` | `LockFile` |
  | `ConfigDiff`, `ConfigChange`, `ConfigChangeSet`, `ConfigChangeOrigin` | The planner (production change view), the confirmation step, previews, `describe()` (pending carry-back) and the `toArray()`/JSON output |
  | `OutcomeRenderer` | `SwitchCommandRunner` and `composerSwitchDescribe()` |
  | `SwitchCommandRunner` | The `composerSwitchDev`/`Prod`/`Update`/`PreviewDev`/`PreviewProd` entry points |
  | `EventContext` | `SwitchCommandRunner`, `OutcomeRenderer` and the describe entry points |

  None is speculative.

## Considered Alternatives

| Decision | Chosen Shape | Alternatives Considered | Trade-Off Summary |
|----------|--------------|-------------------------|-------------------|
| Where the PROD truth lives | `composer.json`, with a transient gitignored snapshot during DEV | Keep committed `composer-prod.json` and harden reconciliation | Two editable truths can only be reconciled heuristically (mtimes). Removing the duplicate removes the problem. |
| Handling DEV edits | Three-way revert carrying user edits back | Block `switch-prod` when DEV `composer.json` differs from the expected transform; or discard edits with a warning | Blocking forces manual copying. Discarding is the current data-loss bug. A three-way merge is precise because the managed entries are known exactly. |
| DEV lock origin | PROD lock + `composer update <local packages>` | Keep saved DEV locks, with the stale-lock detection from the superseded plan | Saved DEV locks drift from PROD versions and go stale whenever PROD changes. Seeding from PROD fixes both at the root. |
| Local package version | Alias to the PROD-locked version, with an optional override | Infer from the local checkout (`git describe`, branch alias); or keep the mandatory pin | Inference depends on the checkout's tags and branch naming. The locked version is always present, needs no git, and is guaranteed to satisfy production's constraints. |
| Running Composer | Plan in `switchTo()`, execute in entry points via `ComposerProcess` (`proc_open` with `COMPOSER_BINARY`) | Programmatic `Composer\Installer` in-process; or chained `@composer` script arrays | In-process reuses a Composer instance loaded from the pre-switch `composer.json` and needs Composer classes. | Stale PROD lock at `switch-dev` | Block with instructions | Auto-run a full `composer update` in PROD first; or proceed with a partial update | A hidden full update changes production versions. A partial update on a stale lock fails inside Composer with a less clear message. |

| Access to Composer's event and IO | One `Utils\EventContext` adapter built from the duck-typed event | `method_exists` probes at each use; typing against `Composer\Script\Event` | Probes at each use scatter the duck-typing and leave PHPStan with `object`. ## Pattern Alignment

- Follows: coded messages (`1822xx`) and exceptions (`1821xx`) with structured context — `docs/agents/project-manifest/constraints.md`. Retired numbers are documented and not reused.
- Follows: the single `FileSystem` choke-point. Snapshot, lock, `installed.json` and status reads and
  writes all go through it, so previews remain exact — `src/Utils/FileSystem.php`.
- Follows: immutable value objects in `src/State/`, and utilities in `src/Utils/` — `tech-stack.md`, `file-tree.md`.
- Follows: no caching in file wrappers — `src/Utils/StatusFile.php` (insight `5d0fa468`).
- Follows: `describe()` never throws — `src/ConfigSwitcher.php`.
- Follows: the three-path convention of `fromProjectRoot()`. The paths are unchanged; only the
  semantics of `composer-prod.*` change.
- **Departure:** the first `enum`s in `src/` (`LockStatus`, `InstalledState`), justified by the
  PHP 8.4 baseline in `constraints.md`.
- **Departure:** the first runtime process execution in `src/` (`ComposerProcess`). This is
  required by the one-command goal. It is kept dependency-free (`proc_open`) so that `symfony/process`
  stays dev-only, and native warnings are captured as in `FileSystem`.
- **Departure:** entry points accept a duck-typed `?object $event`, because the library has no
  dependency on Composer's `Event` class. The same applies to `getIO()`, `isInteractive()`,
  `askConfirmation()` and `write()` (verified on Composer 2.9.5's `Script\Event` / `IOInterface`).
  The probing is confined to `Utils\EventContext::fromEvent()`; every other class takes the typed
  adapter.
- Follows: single-purpose collaborators in `src/Utils/` beside the orchestrator (`FileSystem`,
  `ConfigFile`, `StatusFile`). `SwitchCommandRunner`, `EventContext`, `ComposerProcess` and
  `OutcomeRenderer` extend that split to the entry-point edge.
- Follows: the preview guarantee in `data-flows.md` §5b. Confirmation renders `previewSwitch()`'s
  outcome instead of computing a separate diff.

## Assumptions

- Consumers use Composer 2.x, which writes `content-hash` and provides `COMPOSER_BINARY` and
  `update --with`/`--lock`. Pre-hash locks are `Unknown` and are treated like `Fresh` for planning.
  A Composer 1 project gets a lock status of `Unknown` and `install`, which preserves today's
  behaviour.
- The user accepted removing `reconcile()`, `verify()`, `switch-reconcile` and
  `switch-verify-config`, and changing `composer-prod.*` to uncommitted, by agreeing to fix the
  model "from the ground up" (2026-10-01).
- The single-repository scope holds. The consumers (`mailforge`, `hcp-editor`) are migrated by the
  user after release, so no cross-repository symlink step is needed.
- Non-interactive runs (agents, CI) must pass `--yes`. This is the plan's reading of "always
  confirm" for runs with no one to answer a prompt. The alternative, applying automatically after
  printing, is recorded in Considered Alternatives.
- `ConfigFile::getData()` decodes like Composer's `JsonFile::parseJson()` (both use
  `json_decode(…, true)`), so the hashes agree.

## Constraints

- Zero runtime dependencies (no `composer/composer`, `composer/semver` or `symfony/process` in
  `require`).
- `switchTo()`, `previewSwitch()` and `describe()` never execute processes or prompt. Only entry
  points do.
- No entry point writes a file before confirmation, or skips confirmation when `composer.json`
  would change.
- All file access goes through `FileSystem`. Readers never cache.
- PHP 8.4, `declare(strict_types=1)`, PHPStan clean.
- Retired code numbers are never reused.

## Out of Scope

- Naming the exact unsatisfied constraints when a partial update fails. Composer prints those itself.
- Migrating consumer repositories (see Human Actions).
- The pre-commit guard registry reshape (insight `2cd87f16`).
- Converting `MODE_*` to an enum.
- Previewing lock-level package operations before confirmation. That would mean running
  `composer update --dry-run` as an extra child process. Composer prints the operations as it runs.
- Supporting more than one simultaneous DEV snapshot (e.g. switching DEV between two local sets
  without returning to PROD). A refresh covers changing the local set.

## Acceptance Criteria

- AC-01: `ComposerContentHash::fromConfigData()` equals Composer's `Locker::getContentHash()`
  (golden vectors in Tier 1, parity against the real binary in Tier 2, in PROD and DEV).
- AC-02: `LockFile::getLockStatus()`/`getContentHash()`/`getLockedVersion()` behave as specified
  for missing, non-JSON, hash-less and malformed-config inputs, and in dry-run overlay mode. They
  never throw and never cache.
- AC-03: `LocalRepository` holds the only local-repositories validation. `parseList()` preserves
  the existing error codes and context keys, `parseListLenient()` preserves `describe()`'s existing
  warning texts and per-entry skipping, and the `version` key is optional.
- AC-04: `DevConfigTransformer::apply()` aliases each local package to its PROD-locked version, or
  to the override when given. It keeps the prod root constraint when an alias exists, falls back to
  `*` without `versions` when neither is available, and preserves the existing
  replace/prune/append and underscore-alias behaviour.
- AC-05: `DevConfigTransformer::revert()` satisfies `revert(apply(P), P) == P`. It carries back
  added, removed and re-constrained non-managed packages, edited non-managed keys, and
  added/removed non-managed repositories. It restores managed entries and reports DEV edits to
  them as overridden.
- AC-06: PROD→DEV snapshots the config and lock, keeps the PROD lock as `composer.lock`, writes the
  DEV config, and plans `update <local names>`. With a `Stale` PROD lock it is blocked with no
  file effects. With a `Missing` lock it plans a full `update`.
- AC-07: DEV→PROD writes the carried-back config, restores the snapshot lock, deletes the snapshot,
  and plans per the decision table (`install`, `update <changed>`, `update --lock`, or full
  `update`). It is blocked with no file effects when the snapshot was modified or is missing.
- AC-08: DEV→DEV refresh preserves DEV edits, plans `update <delta>` with `--with` pins for removed
  packages, `install` (when there is no delta and the installed state is `Pending` or `Unknown`),
  or nothing (when it is `Matches`), and is blocked on a modified snapshot. With no delta, the
  refresh does not write `composer.json` (no write operation is recorded) and leaves it
  byte-for-byte unchanged, including non-canonical formatting and after a user's own
  `composer require` in DEV.
- AC-09: PROD→PROD and INITIAL→PROD plan `install` only when the installed state is not `Matches`
  (that is, `Pending` or `Unknown`).
- AC-10: Every outcome carries at most one `ComposerCommand`. `previewSwitch()` reports the
  identical command and file operations as the real switch and leaves the disk untouched.
- AC-11: `switch-dev`, `switch-prod` and `switch-update` execute the planned command via the running
  Composer binary, in one invocation, and exit non-zero on a blocked switch or a failed command.
  `--no-install` prints the command instead. `--with-dependencies` is forwarded to partial updates.
- AC-12: Inside a switcher-launched Composer process (`COMPOSER_SWITCHER_NESTED`), the switch entry
  points no-op with `MESSAGE_NESTED_RUN_SKIPPED`. A consumer's `post-update-cmd: @composer switch-update`
  neither recurses nor rewrites `composer.json`. When the same hook fires after a user-run
  `composer update` or `composer require` (no `COMPOSER_SWITCHER_NESTED`) with an unchanged local
  list, it runs as a normal refresh that leaves `composer.json` unchanged, does not prompt, needs no
  `--yes` even non-interactively, plans no command, and lets the user's command exit 0.
- AC-13: End to end against real Composer:
  1. After a PROD→DEV→PROD round trip, `composer.lock` is byte-identical to the original PROD lock.
  2. The DEV lock differs from the PROD lock only in the switched packages.
  3. A switched package is installed as a symlink aliased to the PROD-locked version, with no
     `version` key configured.
- AC-14: End to end:
  1. `composer require` of a new package while in DEV survives a refresh and `switch-prod`.
  2. After `switch-prod` it is present in `composer.json` and `composer.lock`, and installed.
  3. All other PROD-locked versions are unchanged.
- AC-15: Legacy v2 artefacts (committed-style `composer-prod.*` in PROD, `local-repositories.lock`,
  status files without the new keys) are handled as specified, with `MESSAGE_LEGACY_FILES_FOUND`
  or warnings, and never cause a throw.
- AC-16: `describe()` exposes `lockStatus`, `installedState`, `pendingProdChanges` and the derived
  versions in getters, `toArray()` and `toJSON()`, and still never throws. `composer switch-describe`
  renders them.
- AC-17: `reconcile()`, `verify()`, `VerificationResult`, `RECONCILE_*`,
  `ComposerSwitcherException::KEY_DIRECTION`, `switch_initProductionFiles()`, `switch-reconcile`,
  `switch-verify-config` and the retired codes no longer exist. No `src/` or test reference remains.
- AC-18: Guard 1 of the pre-commit hook instructs a single `composer switch-prod`, and the existing
  `TestGitHooks` coverage passes.
- AC-19: `composer test`, `composer test-integration` and `composer analyze` pass with zero errors,
  warnings or notices. The static `src/` filesystem choke-point scan still passes.
- AC-21: Every switch entry point prints the full `ConfigChangeSet` and the planned command before
  writing anything, with or without `--yes`.
  - Version and constraint changes are marked `[version]`.
  - Carried-back production changes are shown in their own section and marked `[permanent]`.
  - Discarded DEV edits are marked `[discarded]`.
- AC-22: Interactive confirmation behaves as specified.
  - When `composer.json` would change, the entry point asks for confirmation.
  - The default is "no" when there are permanent or discarded changes, and "yes" otherwise.
  - Declining writes nothing, emits `MESSAGE_SWITCH_CANCELLED` and exits 0.
  - Switches with no `composer.json` change (e.g. PROD→PROD `install`) do not prompt.
- AC-23: When `composer.json` would change, a non-interactive run without `--yes` prints the changes, emits
  `MESSAGE_CONFIRMATION_REQUIRED`, throws `ERROR_CONFIRMATION_REQUIRED` (non-zero exit), and leaves
  every file untouched. With `--yes`, it applies in one command. A non-interactive run that leaves
  `composer.json` unchanged (e.g. PROD→PROD `install`) proceeds without `--yes`. The child Composer
  process receives `--no-interaction` when the parent is non-interactive, and does not when it is
  interactive.
- AC-24: The applied change set equals the confirmed one. A second `previewSwitch()` after the
  prompt is compared with the first through `SwitchOutcome::hasSameEffectsAs()`. When an input
  change made during the prompt alters the change set, the planned command, the file operations or
  the blocked state, the switch throws `ERROR_INPUTS_CHANGED` and writes nothing. An input change
  that alters none of them does not abort.
- AC-25: `SwitchOutcome::getConfigChanges()` (and `toArray()`/JSON) expose the same change set to
  API callers, and `describe()` renders pending carry-back with the same structure
  (`pendingProdChanges` is a `ConfigChangeSet`). There is no separate production-change type.
  `switchTo()` never prompts.
- AC-26: The switch, update and preview `composerSwitch*` statics only build an `EventContext` and
  a `SwitchCommandRunner` and delegate; the confirmation sequence, execution and failure mapping
  live in `SwitchCommandRunner`. `method_exists` probing of Composer's event and IO occurs only in
  `EventContext::fromEvent()`, which behaves as specified for a null event, an event without IO,
  and a full Composer event.
- AC-20: The manifest, `AGENTS.md` (§4 decision matrix), `README.md`, `changelog.md` (`v3.0.0`),
  `docs/setup.md`, `docs/usage.md`, `docs/api.md`, `docs/git-hooks.md` and the new
  `docs/migrating-from-2x.md` describe the v3 model, and `docs/migrating-from-1x.md` points to the
  2.x → 3.0 guide. No `AGENTS.md` row tells agents to edit
  `composer-prod.json` or mentions reconcile.

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| **The three-way revert mis-classifies an edit and loses or duplicates data** | Round-trip property tests over a config table; explicit `MESSAGE_MANAGED_ENTRY_OVERRIDDEN` and `MESSAGE_DEV_CHANGES_CARRIED_BACK` listing exactly what moved; `describe()` shows pending carry-back before `switch-prod`; Tier 2 `TestCarryBack` with real `composer require`/`remove`. |
| **The partial update fails because the local package needs newer shared dependencies** | The failure message names `composer switch-dev -- --with-dependencies`, and the files stay in a consistent DEV state, so a re-run is safe (refresh path). |
| **The derived alias is wrong for a local branch that is a new major** | The optional `version` override remains, and `MESSAGE_VERSION_DERIVED` shows which version was used and from where. |
| **A Composer algorithm or CLI change** (`content-hash`, `--with`, `COMPOSER_BINARY`) | Tier 2 parity and end-to-end tests run against the real binary. Docblocks name the verified version (2.9.5). |
| **Recursion via consumer hooks** | The `COMPOSER_SWITCHER_NESTED` guard, pinned by Tier 1 and Tier 2 tests. The docs recommend removing the hook. |
| **A retained `post-update-cmd: @composer switch-update` hook fires after a user-run `composer update`/`require` (guard not set) and fails the user's command, prompts, or rewrites `composer.json`** | Intended behaviour is a normal refresh (Approach "Hook on a user-run update"). With an unchanged local list it is idempotent on `composer.json` (`apply(revert(current)) == current`, and the write is skipped, so the bytes are untouched), so it neither prompts nor needs `--yes`, and plans no command. Only a pending `local-repositories.json` edit makes it show changes and, non-interactively, fail with `ERROR_CONFIRMATION_REQUIRED`; nothing is written, and the message names `--yes`. Pinned by `test_refreshAfterUserRequireIsIdempotent` (Tier 1) and `test_userRunRequireWithHookRetainedIsHarmless` (Tier 2). The migration guide still says to remove the hook. |
| **A consumer upgrades while in DEV under v2** | The existing `composer-prod.*` is consumed as the snapshot. A missing `snapshotHash` skips the tamper check with a warning, and a missing `appliedRepositories` falls back to the current list. Covered by `test_legacyStatusFileDoesNotThrow` and the migration guide. |
| **A git working copy shows `composer-prod.*` deleted until the consumer untracks them** | The migration guide makes `git rm --cached` the first step, and `MESSAGE_LEGACY_FILES_FOUND` explains it on first contact. |
| **Agents or CI scripts break because confirmation is now required** | The failure is explicit and non-zero, and the message names `-- --yes`. The migration guide and changelog list it as a breaking change. Agent instructions in the consumers' `AGENTS.md` are part of the user's migration (Human Actions #2). |
| **The confirmation output is too noisy to read, so users approve blindly** | Changes are grouped by section. Routine `LocalSwitch` changes are listed compactly per package. Only `[permanent]` and `[discarded]` entries get the "no" default. `OutcomeRenderer` tests pin the layout. |
| **Files change while the prompt is open** | Second preview compared through `hasSameEffectsAs()` (`ERROR_INPUTS_CHANGED`), pinned by `test_inputsChangedDuringPromptAborts` and `test_snapshotTamperedDuringPromptAborts`. The window left between the second preview and the real switch is milliseconds, with no prompt in it. |
| **A Composer release renames or reshapes an event or IO method** | All probing sits in `EventContext::fromEvent()`, with documented fallbacks (no arguments, non-interactive, echo). Tier 2 `TestEntryPoints` and `TestConfirmation` exercise it against the real Composer event, and the docblock names the verified version (2.9.5). |
| **Large test rewrite hides regressions** | The decision table is the test oracle. One data-driven preview/real parity test covers every row, and AC-17's reflection check pins the removals. |
| **Interactive prompts or TTY in the child Composer** | Inherited STDIN/STDOUT/STDERR, mirroring `@composer`'s `executeTty()`. Non-interactive parents pass `--no-interaction` through when Composer's own flag was set (read from `EventContext::isInteractive()`), pinned by `test_noInteractionForwardedWhenParentNonInteractive` and its interactive counterpart in `TestEntryPointEdge`. |

## Recommended Workflow
- **Workflow:** ledger
- **Rationale:** This is a breaking model redesign. It spans a new pure transformer, readers, a
  runtime process component, a reshaped orchestrator with removed APIs, rewritten Tier 1 and Tier 2
  suites, and a full documentation overhaul. That warrants staged QA, security review (process
  execution) and architectural review.
